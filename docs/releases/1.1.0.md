# Public Office Watch 1.1.0 release runbook

## Release status

Prepared on branch `codex/published-read-layer-design` from base commit `8bfe7b7`.

This document prepares a release candidate. It does not authorize a production deployment, a Git tag, a push, public grants, PostgREST exposure, a provider switch, or a database promote.

## Release scope

Version 1.1.0 packages the completed performance work:

- compact hybrid `published` shadow layer;
- atomic promote and capacity validation;
- storage-bounded people and search hot paths;
- bounded election/event and race detail paths;
- bounded people, profile, local-office, search, and party contracts;
- compatibility redirect from legacy election links to event pages;
- query-plan and parity evidence for every reviewed public route.

The private published adapter and bridge are intentionally not registered in the runtime provider factory. The deployed frontend continues using its currently configured provider.

## Database state assumptions

The recorded production shadow deployment already contains:

- `202607260007_published_shadow_schema.sql`;
- `202607260008_published_promote.sql`;
- `202607260009_published_query_indexes.sql`;
- `202607280001_published_hot_path_surfaces.sql`.

Before deploying, compare these assumptions with `supabase_migrations.schema_migrations`. Apply only missing migrations, once, in filename order. Do not paste or rerun an already recorded migration.

The later function migrations are additive and consume no meaningful data storage:

- `202607280002_published_person_claims_function.sql`;
- `202607280003_published_election_race_page_function.sql`.

They remain private because the release does not grant frontend execution or expose the schema.

## Capacity gate

Production was last measured at 457,952,403 bytes, with the next promote projected at 511,503,507 bytes and only 12,784,493 bytes of headroom below the 500 MiB allowance.

Before any promote:

1. re-read current production database size;
2. recalculate the projected atomic-refresh peak;
3. require at least 10 MiB of projected headroom;
4. stop if the gate fails;
5. do not add another physical surface in this release.

A code release does not require a promote. Do not automatically call `published.promote` during deployment.

## Required pre-deploy checks

From a clean checkout with the intended public Supabase anon environment:

```bash
npm ci
npm --prefix apps/web ci
npm run check
npm --prefix apps/web run test:browser
npm --prefix apps/web run preflight:production-readiness
gitleaks git --redact --no-banner
```

Release acceptance requires:

- root checks pass;
- five browser smoke cases pass;
- public-view smoke and contracts pass against the intended project;
- published exposure guard confirms the schema remains private;
- gitleaks reports no unignored findings;
- no `.env`, `.env.local`, service-role key, or database password is tracked.

The checked-in `.gitleaksignore` contains only two exact fingerprints from a historical README that quoted gitleaks documentation examples. It does not exclude a path, rule, current file, or branch-wide commit range.

## Dependency audit disposition

Compatible lockfile updates remove the directly fixable PostCSS, js-yaml, Babel, and related findings.

Residual reports require breaking or contradictory changes:

- Vite/esbuild and brace-expansion affect local development and lint tooling, not the generated static site;
- the React Router advisory applies to RSC/server action handling, which this browser-only SPA does not implement.

Do not run `npm audit fix --force` in this release. Track Vite, ESLint, and Router major-version remediation separately and repeat the audit before the next release.

## Deployment order

1. Record the current application artifact, frontend environment, database size, and migration history.
2. Take the normal database backup or confirm point-in-time recovery availability.
3. Apply only missing additive function migrations through the normal migration mechanism.
4. Verify `published` is still absent from PostgREST public schemas.
5. Verify `anon` and `authenticated` still lack `USAGE`, `SELECT`, and published-function execution.
6. Build and deploy the frontend with existing provider environment values unchanged.
7. Do not set a `published` provider value; no such runtime mode is enabled in 1.1.0.
8. Run the post-deploy smoke routes below.

## Post-deploy smoke routes

Verify desktop and mobile layouts where applicable:

- `/` — ticker, county selection, upcoming races, and local-office panel;
- `/regions/taipei-city` — region summary and related races;
- `/elections` — eight grouped event families with the current dataset;
- one legacy `/elections/:electionId` link — redirects to `/elections/events/:eventKey`;
- `/elections/events/2022-2022-11-26-local` — filters and 20-row race page;
- one `/elections/races/:raceId` page — race and candidate detail;
- `/people` — 20-row bounded list, filters, and search;
- one `/people/:personId` page — profile, candidacies, claims, and affiliations;
- `/parties` and one `/parties/:partySlug` page;
- global search for `台北`;
- Chinese/English toggle and horizontal-overflow smoke.

## Rollback

Frontend rollback:

1. redeploy the immediately previous known-good frontend artifact;
2. restore the previous provider environment values if they changed unexpectedly;
3. repeat home, elections, people, and search smoke checks.

Database rollback:

- The two later function migrations are private and additive; leaving them dormant is safer than dropping objects during an incident.
- Do not drop the published shadow layer as part of a frontend rollback.
- If a migration itself fails, rely on its transaction rollback and stop the release.
- Any destructive database reversal requires a separate reviewed plan and backup confirmation.

## Final release actions

After all gates pass and deployment is explicitly approved:

1. merge the reviewed branch;
2. create annotated tag `v1.1.0` on the release commit;
3. push the branch and tag;
4. publish the release notes from `CHANGELOG.md`;
5. record deployed commit, migration history, database size, and smoke results.
